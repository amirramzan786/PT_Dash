# Project Steel — Founding 20 email, verification and status journey

**Status:** Authoritative product copy for GitHub issue #2. Codex should implement this copy and state behaviour unless a platform/security constraint requires a documented deviation.

## 1. Principles

- A Founding place is secured only after **successful email verification plus atomic server-side allocation**.
- Pending/unverified signups do **not** consume a Founder slot.
- Manual approval is not part of the happy path; it exists only for abuse/remediation.
- Public copy must never imply a slot is reserved before verification.
- The first 20 verified legitimate users receive core Steel Premium at £0 for the lifetime of their account.
- #21+ remain eligible for beta/waitlist access, but receive no lifetime Premium promise.
- Do not invent urgency, fake countdowns, fake claimed numbers, or fake testimonials.

## 2. Sender identity

Preferred sender once the Steel domain/email setup exists:

- From name: **Project Steel**
- From address: `hello@projectsteel.co.uk`
- Reply-to: `support@projectsteel.co.uk`

Until the production domain mailbox is configured, use the existing verified transactional sender. Do not hard-code an unverified address.

## 3. Email #1 — verify beta signup

### Trigger
Successful new signup or approved resend for a pending record.

### Subject
**Verify your Project Steel beta signup**

### Preheader
**Verify your email to confirm your beta signup.**

### Body
**You’re one step away.**

You requested access to the Project Steel private beta.

Verify this email address to confirm your signup.

**A Founding 20 place is only secured after verification.** If a place is still available when verification completes, the server will allocate it immediately.

**[Verify my email]**

This verification link is valid for 24 hours.

If you did not request Project Steel beta access, you can ignore this email.

— Project Steel

**Spartan mindset. Spartan strength. Every day.**

### Functional requirements
- Verification CTA must use the actual secure verification URL generated by the implemented flow.
- Link must not expose service-role secrets or founder allocation logic.
- Verification must be idempotent.
- If already verified, following the link again must resolve safely to the existing founder/waitlist result rather than allocating a second record.

**FORGE THE HABIT. BUILD THE BODY. BECOME HARDER TO BREAK.**

### Functional requirements
- Replace `{FOUNDING_NUMBER}` with the server-confirmed number only.
- Do not send before entitlement allocation succeeds.
- If the user already has a Steel account, CTA may become **Open Steel** instead of account creation.
- Founder number must remain stable once legitimately allocated unless an authorised admin remediation explicitly revokes it.

### Preheader
**Verify your email to confirm your beta signup.**

**[Verify my email]**

## 8. Website verification result states

### Verification in progress
Heading: **Securing your place…**
Body: **We’re verifying your email and checking Founding 20 availability.**

Never display a founder number until the server returns the final allocation.

### Founder success
Heading: **You’re Founder #{FOUNDING_NUMBER} of 20.**
Body: **Your core Steel Premium access is locked at £0 for the lifetime of your account.**
Primary CTA: **Create / finish your Steel account**
Secondary text: **Use this verified email so your Founding entitlement stays linked to your account.**

### Waitlist success
Heading: **You’re verified and on the Steel beta waitlist.**
Body: **The 20 lifetime Premium places have now been claimed.**
Primary CTA: **Return to Project Steel**

### Already verified founder
Heading: **You’re already in.**
Body: **Your Founding place is secured. Founder #{FOUNDING_NUMBER} of 20.**
Primary CTA: **Open Steel** or **Finish your account**, based on account state.

### Already verified waitlist
Heading: **You’re already verified.**
Body: **You’re on the Project Steel beta waitlist.**

### Expired link
Heading: **This verification link has expired.**
Body: **Request a new verification email to continue. No Founding place was reserved.**
Primary CTA: **Request a new link**

### Invalid/tampered link
Heading: **We couldn’t verify this link.**
Body: **Request a fresh verification email and try again.**
Primary CTA: **Request a new link**

### Temporary server failure
Heading: **We couldn’t finish verification.**
Body: **Your request has not been lost. Please try again in a moment.**
Primary CTA: **Try again**

Important: a transient failure after identity verification but before UI rendering must not create duplicate founder allocation on retry.

## 10. Account-linking journey

### New Steel user
1. User verifies beta email.
2. Founder/waitlist state is allocated server-side.
3. User follows account CTA.
4. Steel creates/finishes the account using the same verified identity/email.
5. Founder entitlement is attached to the authenticated user ID.
6. Subsequent devices/sessions read entitlement from server-side membership state.

### Existing Steel user with same email
1. Verification identifies the existing account safely.
2. Founder/waitlist record links to the existing `auth.users.id`.
3. Founder entitlement is upserted without disrupting existing app data.
4. CTA becomes **Open Steel** where practical.

### Email mismatch
If a user attempts to complete the account using a different email, do not silently transfer the lifetime entitlement.

Copy:
**Your Founding access is linked to {MASKED_VERIFIED_EMAIL}. Sign in with that email to continue.**

Do not expose the full address unnecessarily on shared/public screens; mask it where appropriate.

## 11. Admin/remediation copy

### Reject obvious abuse
Admin confirmation:
**Reject this beta signup? This removes beta eligibility for this record. No Founder place will be allocated.**

### Revoke a Founder before public launch
Admin confirmation:
**Revoke Founder #{FOUNDING_NUMBER}? This removes the Founding entitlement and may make one place available for deliberate waitlist promotion. This action must be audited.**

Do not automatically promote the next waitlisted user without an explicit authorised action unless a later product rule deliberately changes this behaviour.

### Promote waitlisted user
Admin confirmation:
**Promote this verified waitlisted user into the available Founding place? Allocation and lifetime entitlement must succeed atomically.**

Success:
**Founder #{FOUNDING_NUMBER} allocated.**

## 12. Delivery and security requirements

- Use transactional email infrastructure suitable for production; do not depend on fragile default development email limits for launch.
- Configure SPF, DKIM and DMARC once `projectsteel.co.uk` mail is live.
- Verification URLs must use approved production domains/redirect URLs.
- Do not log verification tokens in plaintext.
- Do not place service-role keys or Turnstile secret keys in browser code or email URLs.
- Resend operations must respect cooldown and rate limiting.
- Email templates should degrade cleanly to plain text.
- Email content must remain readable without remote images.
- Avoid marketing tracking pixels in the verification email unless deliberately introduced later with the appropriate privacy review.

## 13. Analytics events for this journey

Record privacy-conscious server/client events where appropriate:
- `beta_signup_submitted`
- `beta_verification_email_sent`
- `beta_verification_resent`
- `beta_email_verified`
- `beta_founder_allocated`
- `beta_waitlist_allocated`
- `beta_account_linked`
- `beta_verification_expired`

Never put raw email addresses into general analytics event properties.

Useful dimensions:
- signup source (`hero`, `beta-section`, `marketing-site`)
- outcome (`founder`, `waitlist`)
- founder number where appropriate internally
- elapsed time submission -> verification

## 14. QA acceptance matrix

The implementation should prove:

1. New valid signup receives verification email and leaves counter unchanged.
2. Verification within capacity allocates exactly one Founder number and sends Founder confirmation.
3. Verification when full produces waitlist confirmation.
4. Reopening verification link does not allocate again or send contradictory status.
5. Duplicate pending signup gives pending/resend state.
6. Resend cooldown is enforced.
7. Expired verification can restart safely.
8. Existing account with matching email is linked without creating a duplicate identity.
9. Different email cannot claim another account’s Founding entitlement.
10. Founder email is not sent unless founder allocation and entitlement creation succeed.
11. Concurrency at Founder #20 results in one founder and one waitlist user.
12. Email templates contain no secrets or raw debug information.
13. Mobile verification result screens remain clear and fit Steel’s current visual system.
14. All user-facing copy matches this document unless a documented PR deviation is approved.

## 15. Copy hierarchy rule

When a status message conflicts with generic marketing copy, the **server-confirmed status wins**.

Examples:
- Site cached at `19 CLAIMED` but server verification returns waitlist -> show waitlist result.
- Marketing section still says first 20 available but aggregate endpoint returns full -> render `Founding 20 is full. Join the beta waitlist.`
- Never promise a Founder place based solely on client-side state.
